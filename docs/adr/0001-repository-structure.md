# 0001. Структура репозитория

Статус: принято · 2026-09-18

## Контекст
В проекте две части — фронтенд и бэкенд. Они связаны общим форматом данных для синхронизации. А именно отметка рекрутера уходит на сервер с идентификатором, по которому сервер отбрасывает повторы, соблюдая идемпотентность. Иначе, если стороны разойдутся в формате, сервер перестанет узнавать дубли. Разработчик один. 

## Решение
Монорепо на pnpm workspaces, с папками apps/web, apps/api, packages/shared.

## Последствия
+ Общий контракт в одном месте.
+ Один CI 
+ Изменение контракта происходит одним коммитом. Соответственно, проверка происходит на этапе компиляции вместо ошибки в рантайме.
- Повысится пробка хода для нового разработчика в проекте. Сборка с времени начнёт гонять всё подряд. Дочку дать минут только один пакет, и нужно будет её настраивать.
- Нужно настраивать пути в TypeScript.

## Рассмотренные варианты
Был вариант два раздельных репозитория, но тогда нужна согласованность, и изменения в одном репозиторий могли вызвать баги в другом, если они не синхронизованы.
Также был вариант с monorepo и одним package.json. Этот вариант не подходит, потому что тогда смешиваются все зависимости и фронта, и сервера. Не видно проекта, где начинается одно и заканчивается другое, и при сборке нужно следить за тем, чтобы не утащить в бандл не тот код.
