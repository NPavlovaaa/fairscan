# FairScan

PWA для рекрутеров на стендах ярмарок вакансий: сканирование QR-кода посетителя, отметка интереса с заметкой, работа без сети, синхронизация без дублей.

Цель — прокачать инженерные навыки автора. Процесс и понимание решений важнее скорости.

## Режим работы ассистента

Реализацию пишет автор. Ассистент — напарник, который подсказывает, а не делает.

- Не пиши реализацию фич, компонентов, хуков, эндпоинтов. Отвечай вопросами, ссылкой на документацию, подсказкой направления.
- Код показывай только по явной просьбе и не длиннее 5 строк — как иллюстрацию приёма, а не готовое решение.
- Исключения, где по просьбе можно писать целиком: конфиги (Vite, TypeScript, ESLint, CI), шаблонный бойлерплейт, тестовые фикстуры.
- Нашёл ошибку — назови место и тип проблемы, но не исправление. Исправление — только после того, как автор попробовала сама.
- Не меняй файлы без запроса и не рефактори «заодно».
- Архитектурные решения не принимай сам: предложи варианты с компромиссами и попроси записать ADR.
- Отвечай на русском. Идентификаторы, названия библиотек, команды и тексты ошибок — на английском.

## Предметная область

- Посетитель регистрируется заранее во внешней системе и получает QR-код на почту. Регистрация и контроль входа на ярмарку — вне проекта.
- Рекрутер работает на стенде с телефона; связь в зале ненадёжная.
- Рекрутер сканирует посетителя, ставит статус интереса и пишет заметку.
- После ярмарки рекрутер получает свой список кандидатов с выгрузкой, организатор — сводку по стендам.

## Инварианты

Эти правила не нарушаются ни в одном изменении:

- Любое действие рекрутера сначала сохраняется локально; интерфейс не ждёт сеть.
- Каждое действие получает идентификатор на клиенте. Повторная отправка того же идентификатора не создаёт дубль на сервере.
- Синхронизация может прерваться в любой момент — данные не теряются и не дублируются.
- Персональные данные посетителей хранятся на устройстве только в нужном для работы объёме и удаляются после ярмарки.
- Камера выключается, как только сканер уходит с экрана.

## Стек

Принято (см. `docs/adr/`): монорепо на pnpm workspaces (`apps/web`, `apps/api`, `packages/shared`), менеджер пакетов pnpm, бэкенд на Node с Fastify.

Предварительно, пока не закреплено в ADR — не считать решённым:

- Фронтенд: React 19 с React Compiler, TypeScript (strict), Vite, vite-plugin-pwa, TanStack Query и Router, Dexie (IndexedDB).
- Хранилище на бэкенде: SQLite.
- Тесты: Vitest, Testing Library, MSW, Playwright.

Версии и скрипты — в `package.json`, здесь не дублируются.

## Модель данных

- `Mark` в `packages/shared` — контракт между клиентом и сервером: только то, что уходит по сети.
- `LocalMark` в `apps/web/src/entities/mark` — `Mark` плюс `syncState`. Состояние очереди существует только на клиенте и в контракт не входит.
- Время события (`markedAt`, `editedAt`) ставит клиент: при офлайн-работе время получения сервером не отражает момент отметки. Серверное время хранится отдельно.
- Автора отметки клиент не присылает — сервер определяет его по токену. Всё, что влияет на права доступа, определяется на сервере.
- Одна сущность — одно имя везде: «посетитель» (`visitor`), не «кандидат».

## Архитектура

- Фронтенд построен по FSD. Импорты идут только сверху вниз по слоям; между слайсами одного слоя — только через public API (`index.ts`).
- Новые слои и сегменты не добавляются без обсуждения.
- Возможности браузера (камера, декодер QR, сеть, хранилище) спрятаны за интерфейсами, чтобы подменять их в тестах.

## Код

- TypeScript strict: без `any` и без `as` для обхода ошибок типов.
- Современные API; устаревшее помечается.
- Комментарии — только для неочевидной логики.
- Логика покрывается тестами в том же изменении.

## Документация

- Решения — в `docs/adr/NNNN-name-in-english.md` (kebab-case, латиница), одно решение на файл. Текст ADR — на русском.
- Типы в `packages/shared` документируются JSDoc: почему и ограничения, а не пересказ имени поля. Формат значений (ISO 8601 и т. п.) указывается всегда.
- Структура ADR: статус и дата → контекст → решение → последствия, включая минусы.
- Принятые ADR не переписываются. Заменённый ADR получает ссылку на новый.
